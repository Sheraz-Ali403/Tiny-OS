# Building, Running, Inspecting, and Debugging TinyOS (CMake)

## Build tool roles

```text
boot/boot.asm ──NASM -f elf32──> build/boot.o ──┐
                                               │
src/kernel.asm ─NASM -f elf32──> build/kernel.o ─┼─ i686-elf-ld + linker.ld
                                               │         │
                                               │         ▼
                                               └──> build/kernel.elf
                                                         │
                              grub.cfg + ISO tree ────────┤
                                                         ▼
                                                  grub-mkrescue
                                                         │
                                                         ▼
                                                  build/tinyos.iso
                                                         │
                                                         ▼
                                                  qemu-system-i386
```

CMake **coordinates** these steps. It does not generate or compile C/C++ code and doesn't need a C compiler for this project (`project(... LANGUAGES NONE)`).

## Primary CMake workflow

From repository root:

```bash
# Configure after installation, or after changing CMake configuration.
cmake -S . -B build

# Assemble + link boot.o and kernel.o -> kernel.elf.
cmake --build build --target kernel

# Confirm the ELF contains a valid Multiboot v1 header.
cmake --build build --target verify

# Package the kernel and GRUB config into a bootable ISO.
cmake --build build --target iso

# Build ISO if necessary, then boot with QEMU.
cmake --build build --target run
```

**Incremental build:** after editing `src/kernel.asm`, use `cmake --build build --target run`; CMake rebuilds the changed object, relinks, repackages, and starts QEMU. If no source changes, CMake skips unchanged compilation.

Use the optional wrapper `make run`, `make iso`, `make verify`, `make debug`, `make clean`. These invoke CMake rather than defining a second independent compilation process.

## Output files

| Artifact | Generated by | Purpose |
|---|---|---|
| `build/boot.o` | NASM | Entry/multiboot object |
| `build/kernel.o` | NASM | Initial kernel object |
| `build/kernel.elf` | Cross linker | Loadable freestanding 32-bit ELF kernel |
| `build/kernel.map` | Cross linker | Symbol layout/address map |
| `build/iso-root/` | CMake copy steps | Staging directory for ISO |
| `build/tinyos.iso` | `grub-mkrescue` | BIOS-bootable ISO for QEMU |

All generated artifacts are ignored by Git.

## Why use a linker script?

`linker/linker.ld` assigns a conventional starting address of `0x00100000`, puts `.multiboot` early, and arranges `.text`, `.rodata`, `.data`, `.bss`. `.bss` reserves memory at load time without storing thousands of zero bytes inside the image. The initial 16-KiB stack is in `.bss`. The linker symbol `_start` is the ELF entry point.

**Multiboot v1 rule:** the header must be 4-byte-aligned and fully inside the first **8192 bytes of the ELF file**. Merely having a header in a source file isn't enough; verify the final linked ELF using `grub-file`.

## Inspect generated files

```bash
file build/kernel.elf
readelf -h build/kernel.elf
readelf -S build/kernel.elf
readelf -l build/kernel.elf
readelf -s build/kernel.elf | grep -E '(_start|kernel_main)'
objdump -d build/kernel.elf | less
grub-file --is-x86-multiboot build/kernel.elf && echo 'Header OK'
```

`readelf -h` should indicate ELF32 and Intel 80386. `grub-file` exits successfully for a valid Multiboot v1 ELF.

## ISO layout

CMake creates this staging hierarchy automatically:

```text
build/iso-root/
└── boot/
    ├── kernel.elf
    └── grub/
        └── grub.cfg
```

GRUB uses `multiboot /boot/kernel.elf`, not a Linux `linux` command. `set gfxpayload=text` requests the text-mode display expected by the first VGA implementation.

## Boot QEMU manually (equivalent to CMake run)

```bash
qemu-system-i386 -m 128M -cdrom build/tinyos.iso \
  -boot d -no-reboot -no-shutdown
```

`-m 128M` allocates 128 MiB guest RAM. The kernel currently doesn't need all of it. Don't add `-enable-kvm` or change the machine/firmware while establishing the baseline.

## Debug session

Terminal 1:

```bash
cmake --build build --target debug
```

This launches QEMU with `-S` (CPU paused at startup) and a GDB TCP stub at `127.0.0.1:1234`. The port is bound to loopback to avoid exposing remote debugging over the network.

Terminal 2:

```bash
gdb-multiarch build/kernel.elf
```

Within GDB:

```text
set architecture i386
target remote 127.0.0.1:1234
break _start
continue
info registers
x/12i $eip
x/16wx $esp
break kernel_main
continue
```

GDB symbol breakpoints map to the kernel ELF. QEMU begins at firmware/GRUB execution, so you typically `continue` until GRUB loads and jumps into `_start`.

## Clean rebuild

```bash
cmake -E rm -rf build
cmake -S . -B build
cmake --build build --target iso
```

Never run a destructive `rm -rf` with an unreviewed variable or outside the repository's intended build path.

## Extending the build for more Assembly files

For each new NASM source (`src/drivers/vga.asm`, for example): add a separate `add_custom_command(OUTPUT ... COMMAND nasm -f elf32 ... DEPENDS ...)` to `CMakeLists.txt`, include the resulting `.o` in the linker command, and add the object as a linker dependency. Expose shared routines using `global`, import them with `extern`, and agree on a register/stack convention documented in `IMPLEMENTATION_CONTRACTS.md`.

## CMake troubleshooting

- After changing your PATH to include cross tools, **re-run `cmake -S . -B build`**. CMake may cache an old tool path; a fresh `build/` directory is the cleanest recovery.
- `cmake --build build` makes the **kernel ELF** (the `ALL` target); build `iso` to produce the bootable image.
- If `make run` works and direct CMake runs fail, compare the working directories—both expect the repo root.
- `grub-mkrescue` needs the PC/BIOS GRUB modules and ISO utilities. An ISO failure does not mean NASM failed.
